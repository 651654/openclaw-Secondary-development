# 0.8B 视觉模型 × 7B 决策模型联动：深度解析

> 针对本目录已部署的 **OmniJev/PlayJev-0.8B** 与 **Qwen2.5-7B-Instruct (GGUF)** 本地栈。  
> 结论先说：**联动可行，且应把 0.8B 当作「受限选项上的视觉 System One」而不是「看图写长文的描述器」；7B 做 System Two 规划/门控。实时像素控制不要走这条链路。**

## 1. 本地资产与角色

| 组件          | 路径                                     | 原生能力                                             | 在级联中的角色                     |
| ------------- | ---------------------------------------- | ---------------------------------------------------- | ---------------------------------- |
| PlayJev-0.8B  | `omnijev-0.8b/`                          | 一帧图 + 字母选项 → 一次前向 → 选项概率（无 decode） | **感知 + 短名单动作打分**          |
| PlayJev serve | `playjev/` + `scripts/serve_omnijev.ps1` | `/v1/systemone` OpenJev 请求形                       | 视觉侧 HTTP 边界                   |
| Qwen2.5-7B Q4 | `qwen2.5-7b-instruct-q4_k_m-*.gguf`      | 文本指令 / JSON / 工具规划                           | **策略、规则、安全门控、多步计划** |
| Bridge        | `scripts/bridge_vision_decision.py`      | 组装 `openclaw.vision_cascade.v1` 信封               | 契约与编排                         |

PlayJev 的关键不变量（来自上游 `playjev/model.py`）：

- Prompt 冻结为 OpenJev 字母选择题；**不把游戏名/规则写进 prompt**。
- 读出是 **answer 槽位字母 token 的 softmax**，不是自由生成。
- `confidence = (p_max - 1/K) / (1 - 1/K)`，是相对均匀先验的余量，**非校准概率**。
- 官方推理约 **3 GB VRAM / H200 上约 43 ms/步**；本机无 CUDA 时仅适合接线验证。

## 2. 推荐架构（不要用的反模式）

### 2.1 推荐：System One 打分 → System Two 裁决

```text
截图
  │
  ▼
PlayJev-0.8B  /v1/systemone
  │  choice, probabilities[], confidence, timing
  ▼
结构化信封 openclaw.vision_cascade.v1
  │  goal + action_space + perception + uncertainty gates
  ▼
Qwen2.5-7B  (chat/completions, JSON only)
  │  action, reason, use_perception
  ▼
执行器 / 工具 / 安全默认动作
```

这与 PlayJev 训练目标一致：**选项空间已知时，视觉模型直接产可操作分布**。7B 不重新「看图」，只消费可读信号。

### 2.2 反模式 A：0.8B 先写长描述，7B 再决策

- 信息瓶颈大：速度、细小 OCR、遮挡会在自然语言里丢失（PlayJev 自己也列出 motion / tile digits / single-step precision 问题）。
- 延迟双倍：0.8B 若改成生成式描述，就丢掉「单次前向、无 decode」的优势。
- 幻觉会伪装成事实，7B 在错误世界模型上「正确推理」。

### 2.3 反模式 B：全程端到端只跑 PlayJev

适合十款训练过的小游戏闭环；**不适合**开放 UI、业务规则、合规、多工具编排。  
PlayJev 的 general image replay 提升了 MMBench，但仍是 **选择题契约**，不是通用 GUI agent。

### 2.4 反模式 C：7B 多模态端到端吃原图像素

本栈 7B 是 **文本 GGUF**，没有视觉塔。若强行上一体 VLM，会换一套权重与显存预算，不再是「复用现有 7B」。

## 3. 契约设计（深度）

Bridge 使用的信封字段：

```json
{
  "schema": "openclaw.vision_cascade.v1",
  "goal": "...",
  "perception": {
    "choice": "click_primary",
    "confidence": 0.61,
    "probabilities": { "click_primary": 0.55, "wait": 0.2, "...": "..." },
    "ranked": [{ "name": "click_primary", "p": 0.55 }],
    "timing": { "prep_ms": 5, "forward_ms": 40 }
  },
  "action_space": [{ "name": "...", "description": "..." }],
  "uncertainty": {
    "escalate_if_confidence_below": 0.35,
    "forbid_if_top_is": ["abort"]
  },
  "decision_request": { "type": "choice", "instructions": "..." }
}
```

### 3.1 为什么必须「同一套 action_space」

0.8B 与 7B **共享同一 criteria 字典**。否则：

- 视觉打的是 A/B/C，语言规划的是另一套名字 → 无法对齐；
- 7B 可能发明视觉从未评过分的动作。

### 3.2 置信度怎么用（而不是盲信）

| 条件                                   | 建议策略                               |
| -------------------------------------- | -------------------------------------- |
| `confidence` 高且 top 与业务白名单一致 | 7B 可采纳，或甚至跳过 7B（低延迟旁路） |
| `confidence` &lt; 阈值                 | 强制 `wait` / 人工 / 更大 VLM escalate |
| top = `abort` 或禁止类                 | 硬门控，不允许 7B 覆盖为点击           |
| `allowed_mass` 低（若暴露）            | 模型答案槽质量差，视为无效感知         |

PlayJev 文档明确：直接 logits 是 **条件于展示选项的 softmax**，不是校准置信度。生产系统应 **离线标定**（可靠性图）或只用排序 + 阈值。

### 3.3 可选旁路：高置信直通

```text
if confidence >= τ_high and choice in allowlist:
    execute(choice)          # 跳过 7B
else:
    ask_7B(envelope)         # 规划 / 否决 / 改 wait
```

这是真正的 cascade routing：多数简单帧走 0.8B，少数模糊帧付 7B 成本。级联论文里的教训是：**被 escalate 的请求会付「小模型 + 大模型」双份延迟**，因此 τ 要按延迟 SLA 调。

## 4. 延迟与资源预算

| 阶段           | 期望（CUDA）              | 本机 CPU 实测（2026-09-25）       |
| -------------- | ------------------------- | --------------------------------- |
| 0.8B load      | 数秒～十几秒              | **7.3 s**（float32）              |
| 0.8B decide    | ~40–100 ms（H200≈43 ms）  | **forward ≈ 3.2 s**；wall ≈ 3.3 s |
| 信封组装       | &lt;1 ms                  | 同左                              |
| 7B Q4 短 JSON  | 视硬件；通常数百 ms～数秒 | 需另起 GGUF server                |
| 端到端业务决策 | 秒级 OK                   | 控制环 &lt;100 ms **不可行**      |

烟雾测试诊断：合成三色面板上 `allowed_mass≈0` 且 `top_token='I'`，说明全词表最高 logit 不在字母答案槽——**随机/域外画面时选项 softmax 仍可输出，但不能当可靠置信度**。生产必须结合 `allowed_mass` / 置信阈值 / 领域微调。

PlayJev 上游备注：83–100 ms/步时决策会「晚一拍」。再串 7B 后，**不适合 Flappy/Breakout 类反射任务**；适合 RPA、表单、低频运维 UI。

显存粗算（同时常驻）：

- 0.8B bf16 ≈ 2–3 GB
- 7B Q4 ≈ 4–5 GB + KV
- 合计消费级 8–12 GB 卡可尝试；16 GB 更稳。CPU 可跑通逻辑，不谈吞吐。

## 5. 错误模式与缓解

| 失效模式    | 表现                                | 缓解                                                         |
| ----------- | ----------------------------------- | ------------------------------------------------------------ |
| 感知幻觉    | 把广告当成主按钮                    | criteria 写清语义；低置信 wait；ROI 裁剪后再问               |
| 选项集合错  | 画面只有「取消/确定」却问了六类动作 | 每屏模板化 action_space；或两阶段：先问 scene_type           |
| 7B 覆盖视觉 | 无视低置信仍点危险项                | 硬编码 uncertainty 门控，7B 不可绕过                         |
| 分布漂移    | 真实 App 远非训练游戏               | 领域微调 / DAgger；或只把 0.8B 当粗过滤器                    |
| 时序缺失    | 单帧无速度                          | `--two-frame` 训练权重或传前后帧；本 release 默认单帧        |
| OCR 细字    | 448px 读不清                        | 外挂 OCR 并入 `state_text`（PlayJev 支持 frames+text state） |

**强化路径（推荐演进）**：

1. **纯选择题视觉**（现状 PlayJev）
2. **视觉 + OCR/DOM 文本** 写入同一 prompt 的 state
3. **7B 工具调用**（点击坐标由检测器出，7B 只选工具）
4. 需要时再上更大 VLM 作 escalate

## 6. 与「0.8B 转可读信号」上一版讨论的关系

上一版强调「结构化 JSON 感知」。结合本仓库真实模型后，更精确的说法是：

- PlayJev **原生可读信号**就是 `{choice, probabilities, confidence}`，不是段落描述。
- Bridge 把它 **升维** 为带 goal / action_space / gates 的信封，才交给 7B。
- 若业务需要 bbox、OCR、控件树，应 **另接专用感知**，再与 PlayJev 概率合并进同一信封——不要强迫 0.8B 生成这些字段。

## 7. 验证矩阵（建议按此证明）

| 检查           | 命令 / 方法                                | 通过标准                            |
| -------------- | ------------------------------------------ | ----------------------------------- |
| 权重大小与文件 | `omnijev-0.8b/model.safetensors` ≈ 2.21 GB | 存在且完整                          |
| 单次决策烟雾   | `scripts/check_omnijev.py`                 | 返回 4 选项概率和 `ok`              |
| HTTP 契约      | `serve_omnijev.ps1` + POST `/v1/systemone` | JSON answers + timing               |
| 信封形状       | `bridge_vision_decision.py --dry-run`      | `schema=openclaw.vision_cascade.v1` |
| 双模型联调     | vision URL + llm URL                       | 7B 输出合法 `action` ∈ action_space |
| 门控           | 人为降低置信 / 强制 abort                  | 不执行危险动作                      |
| 延迟           | 量 `prep_ms+forward_ms` + 7B TTFT          | 满足业务 SLA                        |

## 8. 最终建议

1. **默认联动形态**：PlayJev 打分 → 信封 → 7B JSON 裁决 → 执行器。
2. **高置信旁路** 降低平均延迟；**低置信硬门控** 保证安全。
3. **不要**把 PlayJev 当 caption 模型；**不要**在反射控制环里串 7B。
4. 本机先用 CPU 跑通契约；上 CUDA 后再谈自动化吞吐。
5. 7B GGUF 需单独起 OpenAI 兼容服务后，用 bridge 的 `--llm-url` 完成闭环。
